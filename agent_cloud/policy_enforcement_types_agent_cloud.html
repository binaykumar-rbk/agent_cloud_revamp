      • Introduction to Agent Cloud

        Describes what Agent Cloud does, how it works, the key concepts and terms, and the features that are available in early access.

      • Get started with Agent Cloud

        To start using Agent Cloud, confirm the prerequisites, deploy a data plane, connect your agents, verify the setup, and then add policies.

      • Deploy your data plane

        The Agent Cloud data plane runs as a SaaS deployment that Rubrik operates, or in your own AWS VPC or Azure VNet. Decide where it runs before you connect your AI providers and agents.

      • Connect your agents

        A connection links Agent Cloud to a source of agent activity, such as an enterprise AI platform, a gateway that your custom agents use, or the endpoint detection binary on employee devices.

      • Discover and observe

        Agent Cloud builds an inventory of the agents, tools, identities, models, and MCP servers in your environment, and records what each agent does, session by session.

      • Govern and control

        Agent Cloud policies are the governance rules that define the acceptable behavior for your AI agents. Use them to detect risky activity and, on connections that support it, stop it.

        • How policies work

          A policy is a named rule with a severity that Agent Cloud evaluates against your agents, tools, and sessions. When agent activity breaks a policy, Agent Cloud records a violation or an alert and, depending on the policy's enforcement mode, can stop the action.

        • Enforcement modes

          A policy's enforcement mode determines what happens when agent activity breaks it: Monitor records an alert, Block stops the action before it runs, and Ask hands the action to the agent's own approval prompt.

        • How blocking works

          A Block policy lets Agent Cloud stop an agent action before it takes effect, inline with the agent's own execution, instead of only flagging it afterward.

        • Agent Cloud system policies

          Agent Cloud includes multiple system policies. These policies are not enabled by default. You can enable them from the Policies page.

        • Agent Cloud policy packs

          Agent Cloud policy packs are curated collections of system policies you can add to your Agent Cloud account to enable a focused set of controls for a specific risk area, compliance framework, or industry.

        • Custom policies

          A custom policy is a rule that you write in plain English. The Semantic AI Governance Engine (SAGE) turns it into a policy that it judges against agent activity by intent, not by matching keywords.

        • Alerts and violations

          Alerts and violations are the findings that your policies produce. An alert is a specific action or message that broke a policy. A violation is a standing configuration that breaks one.

        • Viewing insights

          View the Insights page to review security recommendations and posture improvements identified by Agent Cloud.

        • MCP access policies (Early access)

          An MCP access policy decides which identities can use an MCP server, or a specific tool on it, through your MCP gateway.

      • Rewind agent actions

        Agent Rewind undoes the changes that an agent action made to your data by restoring the affected objects from Rubrik backups, without rolling back the entire workload. You can start a rewind from the Sessions page, or from any page that displays the action or alert detail tray. Rewind requires a complete Rubrik snapshot taken within seven days before the action.

        Control who can see and manage Agent Cloud, review platform and user activity, understand who is responsible for each part of a deployment, and follow best practices for rollout and for building agents that are easier to govern.

Enforcement modes

A policy's enforcement mode determines what happens when agent activity breaks it: Monitor records an alert, Block stops the action before it runs, and Ask hands the action to the agent's own approval prompt.

Ask is not enabled on all accounts. To enable it, contact your Rubrik account team.

This table compares the enforcement modes.
Mode What happens When to use it
Monitor The action proceeds, and Agent Cloud records a policy alert after it captures the session. Works on every connection that captures session activity. New policies, and policies that you want to observe before you enforce them. Monitor is the default for new policies.
Block Agent Cloud stops the action before it runs, on connections that support blocking, and records a policy alert. On other connections, the action proceeds and an alert is recorded, as in Monitor. Policies that have produced the alerts you expect in Monitor mode, for actions that are risky enough to stop.
Ask Agent Cloud hands the tool call to the agent's own approval prompt, and the user decides whether it runs. Where Ask is not supported, the policy falls back to Monitor or Block. Actions that are sometimes legitimate, where you want the person using the agent to confirm them.

For how blocking works, including what each connection can block and its limitations, see How blocking works. For Ask, see Ask: human approval.

Which policies can block

  • Policies with structured rules, naming specific tools, agents, or models, can always be set to Block.
  • Custom natural-language policies can always be set to Block.
  • Some system policies cannot be enforced in real time. They offer Monitor only.

Monitor

Monitor enforcement lets the action proceed without interruption. Agent Cloud records a policy alert, which is available for review in the activity log.

Monitor is the default enforcement type for new policies. It is appropriate for observing AI agent behavior and establishing a baseline before applying stricter enforcement.

Block

Block enforcement prevents an action from executing. Agent Cloud intercepts the action in real time and records a policy alert.

Block enforcement requires a connection that supports tool blocking. For connections that do not support blocking, Agent Cloud records an alert but lets the action proceed, consistent with Monitor enforcement.

When you select Block enforcement for a policy, you can specify the message types that Agent Cloud blocks. The types include:
  • User prompts
  • Agent responses
  • Tool calls
  • Tool responses

If you select some, but not all, of the message types, the unselected types fall back to Monitor enforcement. For those types, Agent Cloud records a policy alert but does not block the messages.

Plan your policy rollout

Introduce policies in Monitor mode, review the alerts they produce, and move a policy to Block only after it behaves as you expect and only on connections that support blocking.

Warning:
Blocking fails open. If Agent Cloud cannot reach a decision in time, the action proceeds. Most connections cannot block at all. Do not rely on Block as your only control. For more information, see Blocking limitations and fail-open behavior and Blocking support by connection.

Rollout sequence

  1. Start in Monitor. Enable system policies or policy packs in Monitor mode first, and review the alerts they produce before you enforce anything.
  2. Test custom policies before you enforce them. Use the strength rating, test with sample input, and backtest against past sessions to check that a policy flags what you intend and nothing else. For more information, see Testing a custom policy using manual input and Testing a custom policy using a backtest.
  3. Move to Block deliberately. Switch a policy to Block only after it has produced the alerts you expect, and only for connections that support blocking. Check Blocking support by connection first.
  4. Review insights regularly. Insights point to risky behavior that your policies do not cover yet. Turn the ones that matter into policies, and dismiss the rest. For more information, see Viewing insights.
  5. Triage on a schedule. Review open alerts and violations regularly, and mark legitimate, recurring activity as safe so that real issues stand out. For more information, see Alerts and violations.
  6. Grant session viewing narrowly. Session content can contain sensitive data. Give the View Session Timelines and Summaries privilege only to the people who investigate sessions. For more information, see Granting session viewing access.

Is this policy ready for Block?

This table lists the questions to answer before you move a policy from Monitor to Block.
Question If yes If no
Has the policy run in Monitor long enough to produce the alerts you expect? Continue. Stay in Monitor.
For a custom policy, did you test it with sample input and a backtest, and is the strength rating acceptable? Continue. Edit and test the policy again.
Does the policy support Block? Some system policies offer Monitor only. Continue. Keep the policy in Monitor.
Does the connection that the agents use support blocking the message types you selected? Continue. Block behaves like Monitor on that connection. The action proceeds and an alert is generated.
Can you accept that blocking fails open if a decision times out or the enforcement service is unreachable? Switch the policy to Block. Add compensating controls, or keep the policy in Monitor.
