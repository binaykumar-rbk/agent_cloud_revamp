    • Agent Cloud with RSC

      Agent Cloud with RSC provides a comprehensive solution for discovering AI agents in your environment, understanding which tools they have access to, detecting risky actions they perform on your data and configurations, and rewinding unauthorized changes without downtime.

      • Introduction to Agent Cloud
      • Get started with Agent Cloud

        To start using Agent Cloud, confirm the prerequisites, deploy a data plane, connect your agents, verify the setup, and then add policies.

      • Choose your data plane

        The Agent Cloud data plane runs as a SaaS deployment that Rubrik operates, or in your own AWS VPC or Azure VNet. Choose where it runs before you connect your AI providers and agents.

      • Connect your AI agents

        A connection links Agent Cloud to a source of agent activity, such as an enterprise AI platform, a gateway that your custom agents use, or the endpoint detection binary on employee devices.

      • Discover and observe

        Agent Cloud builds an inventory of the agents, tools, identities, models, and MCP servers in your environment, and records what each agent does, session by session.

      • Manage Agent Cloud policies

        Agent Cloud policies are the governance rules that define the acceptable behavior for your AI agents. Use them to detect risky activity and, on connections that support it, stop it.

      • Rewind AI agent changes with Agent Cloud

        Agent Rewind undoes the changes that an agent action made to your data by restoring the affected objects from Rubrik backups, without rolling back the entire workload. Rewind requires a complete Rubrik snapshot taken within seven days before the action.

      • Administer Agent Cloud

        Control who can see and manage Agent Cloud, review platform and user activity, understand who is responsible for each part of a deployment, and follow best practices for rollout and for building agents that are easier to govern.

        • Access control for Agent Cloud

          Agent Cloud separates seeing what it found from reading what agents said. Session content is the most sensitive data that Agent Cloud holds, so viewing it requires its own privilege, which no built-in role includes.

        • Event log and audit log

          The event log records platform activity in Agent Cloud, such as policy updates and connection changes. The audit log records who did what. Open both from the Events menu.

        • Responsibilities by role

          Who is responsible for each part of an Agent Cloud deployment: the customer, Professional Services, or Rubrik Support.

Best practices for AI agents managed by Agent Cloud

Follow these practices to roll out Agent Cloud safely and to get the most accurate inventory, monitoring, and enforcement for your agents.

Which practices apply to you

This table shows which best practices apply to each kind of agent.
Your agents Practices that apply
Everyone Part 1, Rolling out Agent Cloud.
Native integrations (enterprise AI platforms) Identity and service principal usage, and agent naming where the system prompt is configurable.
Custom agents that you build All practices in Part 2.

Part 1: Rolling out Agent Cloud

  • Start in Monitor mode. Review the alerts that your policies produce before you enforce anything. For the full approach, see Plan your policy rollout.
  • Remember that blocking fails open, and that most connections cannot block. See Blocking limitations and fail-open behavior.
  • Review insights and triage open alerts and violations on a schedule. Mark legitimate, recurring activity as safe so that real issues stand out.
  • Grant session viewing narrowly, because session content can contain sensitive data. See Access control for Agent Cloud.
  • Protect the data that your agents change. Agent Rewind needs a Rubrik backup taken within seven days before an action. See Rewind AI agent changes with Agent Cloud.

Part 2: Building agents that are easier to govern

The following practices apply to custom agents that you build.

Name the agent in its system prompt

A specific name helps an AI agent maintain its boundaries and role definition during long contexts.

AI models can lose track of their specific role or context in complex or multi-turn conversations. Explicitly defining their identity prevents identity drift and assists with tracking during multi-agent workflows.

When reviewing execution traces or conversation logs within Agent Cloud, having the AI agent state its name makes it much easier for developers to identify which AI agent produced which output in a multi-agent system.

This table compares a system prompt that does not name the agent with one that does.
Avoid Recommended 
You are a helpful assistant that analyzes financial spreadsheets.
This example does not provide the AI agent's name, which makes the instruction ambiguous and creates opportunities for identity drift and hallucinations.		 
You are FinanceBot, an automated data analyst.
Your primary role is to inspect quarterly spreadsheets.
This example names the AI agent, which helps prevent identity drift and provides a solid framework for its operations.

Use descriptive tool names

Large language models (LLMs) use only semantic meaning to determine which function or API to call. Vague or generic names lead to tool routing errors or model hallucinations.

Tool names function as strict API endpoints. Each name should communicate the precise action it performs. Rubrik recommends that you name your tools using unambiguous identifiers, separating words with underscores (action_object_modifier) or using snake_case or camelCase conventions.

This table compares ambiguous tool names with descriptive tool names.
Avoid Recommended
tool1 fetch_user_billing_history
process_data calculate_mortgage_amortization
run_script delete_expired_session_tokens
db_helper —

Build single-purpose tools

Combining multiple functions into a single tool can confuse AI agents about which parameters to pass and can increase the security risk if the tool is misused.

Separating create, read, update, and delete operations into distinct tools makes it easier for the model to choose the correct function, and lets Agent Cloud classify each tool's capabilities and apply policies to destructive tools without restricting read-only ones.

For example, if an AI agent needs to read data, you can safely grant it access to a read_user_profile tool without providing access to the manage_user_profile tool, which can also manage deletions.

This table compares a multi-purpose tool with single-purpose tools.
Avoid Recommended
database_manager Three distinct tools for querying, updating, and removing: query_inventory_stock, update_item_price, and remove_discontinued_product.

Write detailed tool descriptions

Tool descriptions serve as the manual that the LLM reads at runtime to understand the tool. If a tool lacks a description or provides a vague one, the LLM either guesses how to use the tool or ignores it entirely.

A good tool description explains when the tool should be used and when it should not be used. Rubrik recommends that you document the format, constraints, and data types that the tool's inputs expect.

This table compares a vague tool description with a detailed one.
Avoid Recommended
Fetches customer info 
Use this tool ONLY when a user explicitly asks for their account
status or subscription level. Do not use for billing issues. Requires
a valid 10-digit 'customer_id' string formatted as CUST-XXXXXX.

Use identities and service principals

Agent Cloud must map the AI agent's background actions to an enterprise-grade identity to prevent unauthorized data access and maintain a strict audit trail.

Rubrik recommends assigning appropriate identities to agents so that Agent Cloud can determine which service principal an AI agent is using, or on which user's behalf the agent is acting.

Binding an agent to a specific service principal, such as an AWS IAM Role, an Azure Service Principal, or an OAuth token, ensures that the AI agent cannot access enterprise resources beyond its designated scope. When an agent acts on behalf of a logged-in user, it must inherit that specific user's permissions dynamically, preventing privilege escalation.

Correctly configured identities let security teams review database and API logs to determine which AI agent executed a command, which minimizes enterprise security risks.
